# 0.5.0 — A BOM describes one agent

Before this release an Agent BOM described a *place*: `scan endpoint` resolved
one config directory and `scan repo` walked one tree, each emitting one document
whose subject was that place. "Which agent is affected by this vulnerable MCP
server?" was unanswerable — the document could only say *this place has it*.

Now a BOM describes one **agent**: one runtime plus the composed context it
loads. A scan emits as many documents as agents it discovers, which is one
today, because Claude Code is still the only runtime OpenACA supports. No second
runtime ships here — what changes is that document count is a consequence of
discovery rather than an assumption baked into the scanner.

Design: `docs/specs/multi-agent-support.md`. Decisions: ADR-0044 (the agent is
the BOM root), ADR-0045 (keying), ADR-0046 (coverage), ADR-0047 (output shape).

## Highlights

- **The agent is `metadata.component`.** Its `bom-ref` is `root/claude-code`,
  its `name` is `Claude Code`, and it carries `openaca:agent_kind`,
  `openaca:composition_source` (`installed` or `declared`, always explicit), and
  `openaca:composition_coverage`. Schema version is `0.5`.

- **Coverage is a per-scan verdict.** `openaca:composition_coverage` states how
  much of an agent's composition the scan could observe, resolved per
  composition source as `min(baseline, evidence)` — so a manifest that failed to
  parse downgrades `complete` to `partial` instead of a scan that skipped a file
  still claiming completeness.

- **`scan repo` and `bom repo` are agent-rooted too.** A repo scan now discovers
  the agents a tree *declares* and emits one document each with
  `composition_source: declared`. A tree declaring no agent — a repository of
  ordinary package manifests — emits nothing and exits `0`. Evidence is a file
  the runtime owns; an empty `.claude/` directory is not evidence, and neither
  is a bare `mcp.json`, which no runtime owns exclusively.

- **Findings carry their agent.** The findings list stays flat — one SARIF path,
  one exit code, one `sarif-path` output, so the reference Action is unchanged —
  but every advisory, posture, and observation row now says which agent it
  belongs to, and each finding's composition lineage resolves against that
  agent's own graph. Text output prints one card per agent; `--format json`
  emits one document with a new `agents[]` array, so an installed agent with
  nothing configured still appears.

- **An installed runtime with no configuration is a real agent.** It is reported
  with zero components rather than being invisible — the deliberate asymmetry
  with a repo declaration.

## Breaking changes

- **Every `bom-ref` in the installed path is renamed once.** Node-key root
  labels name the kind that owns the config root, so `endpoint/<rel>` becomes
  `claude-code/<rel>`. Diffs match on `bom-ref`, so the first `openaca bom diff`
  after upgrading reports every component removed and re-added, and earlier diff
  history is not comparable across this boundary. No data is lost. There is
  deliberately no version-aware diff shim: it would be migration code to carry
  and later retire, to suppress a one-time event that is noisy rather than
  harmful. Repo-path component `bom-ref`s are unchanged.

  Uploads are **not** affected: the remote collector still emits `endpoint/`
  keys and the `openaca:target` root, so locally emitted and uploaded `bom-ref`s
  do not agree until the collector is migrated.

- **`bom endpoint`/`bom repo` default to NDJSON on stdout** — one CycloneDX
  document per line. A single agent is a single line, so `jq` and `json.load`
  keep working, but the output is compact rather than indented. Use
  `--output-dir <dir>` for one file per agent; `--output` is deprecated and
  errors with a pointer to `--output-dir` only when more than one agent
  resolves. `scan bom --input` accepts either shape.

- **Three properties stop being written**: `openaca:target_type`,
  `openaca:agent_host`, and `openaca:runtime_hosts`. All three are still *read*
  from stored `0.4` documents — removing a property means stopping the write,
  not the read. A component's "active in" now comes from the agent that scanned
  it rather than from the parser that read the file, which is a stronger and
  correct claim: one consequence is that a VS Code `servers` block, previously
  rendered with an empty `active_in`, now names the scanning agent.

- **`scan repo` text output** gains a `coverage` row in its Target block, and its
  `host surface` reads `Claude Code` rather than `repository`.
